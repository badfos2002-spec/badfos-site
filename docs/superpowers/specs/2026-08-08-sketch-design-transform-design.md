## 3. מודל הנתונים

```ts
export type DesignTransform = {
  dx: number    // הסטה אופקית, במערכת הצירים של המקרן (יחידות מקומיות של הבגד)
  dy: number    // הסטה אנכית
  scale: number // מכפיל גודל; 1 = ברירת המחדל הנוכחית
}
```

נצמד לכל רשומת עיצוב:

```ts
designs: { area: string; areaName: string; imageBase64: string; transform?: DesignTransform }[]
```

**השדה אופציונלי.** לסקיצות שנוצרו לפני השינוי אין `transform` ולכן ייראו בדיוק כמו היום — אין מיגרציה.

`lib/firebase.ts` משתמש ב-`getFirestore` בלי `ignoreUndefinedProperties`, ולכן `transform: undefined` בתוך המערך **יזרוק** ב-`addDoc`. השדה נכתב רק כשהוא שונה מ-`{dx:0, dy:0, scale:1}` — דרישה קשיחה, לא סדר.

## 4. איך הכוונון מוחל על התלת-ממד

### 4.1 העיקרון — הסטה במערכת של המקרן

כל אזור הדפסה הוא `Decal` — מקרן עם `position`, `rotation`, `depth`. הזזה **בתוך המישור של המקרן עצמו** מחליקה את חלון ההטלה על פני הבד:

```ts
function withTransform(p: Placement, t?: DesignTransform): Placement {
  if (!t || (t.dx === 0 && t.dy === 0)) return p
  const off = new THREE.Vector3(t.dx, t.dy, 0).applyEuler(new THREE.Euler(...p.rotation))
  return { ...p, position: [p.position[0] + off.x, p.position[1] + off.y, p.position[2] + off.z] }
}
```

אימות (שירה): `DecalGeometry` בונה `projectorMatrix` מה-euler והמיקום, וגוזר את החיתוך וה-uv בצירים המקומיים של המקרן. drei מאפס את `matrixWorld` של הרשת האב לפני הבנייה ([Decal.js:52-53](../../../node_modules/@react-three/drei/core/Decal.js#L52-L53)), כך שהמיקום נמדד במרחב המקומי של הבגד. z לא נוגעים בו — חלון העומק שמפריד קדמי מאחורי באותה רשת נשמר.

מקרה `back` (`rotation: [0, π, 0]`): `R_y(π)·(dx,dy,0) = (−dx, dy, 0)`; קבוצת ה-`Turntable` גם היא ב-`R_y(π)`, ולכן בעולם: `(+dx, dy, 0)`. המצלמה ב-+z, כלומר **+dx = ימינה על המסך גם בגב**. אין צורך בטיפול פרטני.

### 4.1.1 אינוריאנטה: רק שני סיבובים קיימים

בכל 15 הווריאנטים ב-`VARIANTS`, `Placement.rotation` הוא **תמיד** `[0,0,0]` או `[0, π, 0]` — והשני מופיע אך ורק על אזורים שנקראים `back`, בהתאמה מושלמת לכלל של `Turntable` (`focusArea === 'back' ? π : 0`).

זה לא פרט טריוויה — §5.4 **תלוי** בו. `R_y(π) = diag(−1,1,−1)` מתחלף (commutes) עם שינוי קנה מידה מיושר-צירים, ולכן ההצמדה `R·diag(s,s,1)·Rᵀ` מתאפסת לכדי `diag(s,s,1)` ואפשר לבטא את התצוגה המקדימה עם `position`/`scale` פשוטים של `Object3D`.

> ⚠️ **אם אי פעם יתווסף placement עם סיבוב נטוי** (שרוול, פאנל צד של כובע) — התצוגה המקדימה בזמן גרירה תייצר דקאל **מגזר (sheared)** בשקט. התיקון היחיד אז: `matrixAutoUpdate = false` ובנייה ידנית של `T(P+Δ)·R·S·R⁻¹·T(−P)`.

**החזרה המוקדמת כש-`dx==0 && dy==0` היא פונקציונלית, לא אופטימיזציה:** היא משמרת את זהות האובייקט של ה-placement המקורי, וכך סקיצות ללא כוונון לא משלמות שום מחיר ולא מפילות memoization.

### 4.2 גודל

`artworkScale()` מבצע contain-fit של התמונה בתוך תיבת המדריך תוך שמירת יחס. המכפיל מוחל על **שני** מסלולי ההחזרה — גם מסלול ה-`box` וגם מסלול ה-fallback לפי `placement.size` (הכובעים משתמשים בו, כי ל-`CAP_AREAS.front_full` אין `GuideBox`).

`placement.depth` **לא** מוכפל: הוא עומק ההטלה על המשטח המעוקל, לא מידה של האומנות. הכפלתו הייתה שואבת גיאומטריה מהצד הרחוק.

הסינר עובר במסלול `SheetShirtDecal` הנפרד, שמזין את `dw`/`dh` מ-`artworkScale` אל `useSheetDecalGeometry` — כלומר הוא יורש את המכפיל בלי שינוי נוסף.

### 4.3 תיקון חובה ב-`useSheetDecalGeometry` (סינר)

ההוק ממומו על `[target, placement, w, h]` — `placement` **לפי זהות אובייקט**. `withTransform` מחזיר אובייקט חדש בכל רנדר, ולכן ברגע ש-`dx/dy ≠ 0` ה-memo יחטיא בכל רנדר (בחירת צבע, כל שינוי state בעמוד), ויבנה מחדש `DecalGeometry` של 13k משולשים.

בנוסף, בניגוד ל-`<Decal>` של drei שמשחרר ב-cleanup, ההוק **לא משחרר** את הגיאומטריה הקודמת — דליפת GPU.

**התיקון:** לממומו על המספרים (`placement.position[0..2]`, `placement.rotation[0..2]`, `w`, `h`, `placement.depth`) ולהוסיף `dispose` ב-cleanup.

## 5. מנגנון השליטה

### 5.1 המצב הקיים

אין `OrbitControls`. יש `Turntable` מותאם ([Preview3DStage.tsx:32-97](../../../components/designer/three/Preview3DStage.tsx#L32-L97)): גרירה אופקית מסובבת סביב Y, `touch-action: pan-y` מאפשר גלילת דף בגרירה אנכית, אין זום ואין צביטה. לכן אין התנגשות מחוות אמיתית — צריך רק להחליף את מטפל המצביע במצב עריכה.

### 5.2 כניסה ויציאה ממצב עריכה

בכניסה על אזור:
1. `editArea` מוגדר → `Turntable` מקבל `focusArea` חדש ומכוון את המודל לאזור.
2. **סנאפ מיידי — חייב לקבוע את שניהם.** ה-`useFrame` הוא `g.rotation.y += (target.current − g.rotation.y) * 0.15`, ולכן קביעת `group.rotation.y` לבדה **מתבטלת בפריים הבא** ומתכנסת חזרה ליעד הישן. יש לקבוע גם `target.current`, ובאותה נרמול "הדרך הקצרה" שבשורות 50-54 — אחרת שינוי המיקוד הבא ייקח את הדרך הארוכה. (בלי הסנאפ, ה-lerp לעולם לא מגיע בדיוק ליעד וגרירה בחצי השנייה הראשונה ממפה כיוונים שגוי; §5.3 מניח בדיוק 0 או π.)
3. `Turntable` ננעל — הגרירה לא מסובבת.
4. `touch-action` על ה-canvas עובר ל-`none`, כדי שגרירה אנכית תזיז ולא תגלול.

ביציאה: הכול מוחזר.

**מלכודת חובה:** ה-effect של מטפלי המצביע ב-`Turntable` תלוי ב-`[gl]` בלבד. קריאת `locked` כמשתנה בתוך `down`/`move` תילכד ב-closure של הרנדר הראשון והנעילה לעולם לא תתפוס.

**הפתרון היחיד הוא `useRef` שמתעדכן ב-effect נפרד.** אסור להוסיף את `locked` לתלויות: הפעולה הראשונה של אותו effect היא `el.style.touchAction = 'pan-y'` ([Preview3DStage.tsx:58-59](../../../components/designer/three/Preview3DStage.tsx#L58-L59)), ולכן כל החלפת נעילה תריץ אותו מחדש ותדרוס את ה-`touch-action: none` שמצב העריכה בדיוק הגדיר — כלומר במובייל הכניסה למצב עריכה תשמר בשקט את גלילת הדף, בדיוק התסמין שסעיף זה קיים כדי למנוע, ועוד עם מרוץ בין שני ה-effects.

**מלכודת שנייה:** ה-effect של `focusArea` רץ רק כשהערך **משתנה**. תרחיש: בוחרים אזור → עורכים → יוצאים → מסובבים ידנית 90° → נכנסים שוב לאותו אזור. `focusArea` לא השתנה, המודל נשאר מסובב, ו-+dx כבר לא ימינה. הכניסה למצב עריכה חייבת לכפות את זווית היעד, לא להסתמך על שינוי `focusArea`.

### 5.3 המרת פיקסלים ליחידות מודל

`Bounds fit clip` מזיז את **המצלמה** ולא משנה קנה מידה של האובייקט ([Bounds.js:135-138](../../../node_modules/@react-three/drei/core/Bounds.js#L135-L138)); בלי `observe` הוא מתאים פעם אחת בלבד לכל mount. לכן היחס מחושב חי, בזמן הגרירה:

```ts
const { camera, size } = useThree()
if (!(camera instanceof THREE.PerspectiveCamera)) return  // ← חובה: RootState.camera הוא
                                                          //   Orthographic | Perspective, ו-.fov
                                                          //   לא קיים על האיחוד. בלי הצרה
                                                          //   `npx tsc --noEmit` ייכשל.
const dist = camera.position.distanceTo(anchorWorldPos)
const visibleH = 2 * Math.tan((camera.fov * Math.PI / 180) / 2) * dist
const unitsPerPx = (visibleH / size.height) / anchorWorldScale
```

```ts
dxLive += deltaPxX * unitsPerPx
dyLive -= deltaPxY * unitsPerPx   // ציר Y של המסך יורד
```

**מאיפה `anchorWorldPos` ו-`anchorWorldScale`:** `Tshirt3DModel` מרנדר, כש-`editArea` מוגדר, `<object3D>` בלתי-נראה במיקום ה-placement **בתוך רשת היעד**, ומעביר את ה-ref שלו למעלה. מכאן `getWorldPosition()` ו-`getWorldScale()` נכונים בהגדרה.

`size.height` של R3F הוא **פיקסלי CSS**, בדיוק כמו הדלתאות של `e.clientX/Y` — התאמה נכונה. אין להחליף ל-`gl.domElement.height` (פיקסלי מכשיר, פי 2 ברטינה).

את העוגן יש לקרוא ב-`pointerdown` — אחרי שרונדר לפחות פריים אחד — ולא ב-effect שיוצר אותו, אחרת `matrixWorld` עדיין זהותי.

**למה לא לקחת את הרשת ישירות:** `meshes` הם שיבוטים מ-`scene.clone(true)` שמעולם לא נוספים לסצנת R3F — ה-`matrixWorld` שלהם משקף את היררכיית ה-GLB, בעוד שהרכיב **משטח** את ההיררכיה ומרנדר `position/rotation/scale` מקומיים בלבד תחת קבוצת `normScale`. מדידה: בפולו `getWorldScale()` על השיבוט מחזיר **38.075** מול 1.0 האמיתי; בהודי/סווטשירט/זיפ ~0.41; בווסט 0.33. שימוש בשיבוט = באג פי 38.

**בדיקת שפיות:** `normScale = 2/maxDim`, ו-gltfpack מרווה ציר אחד ל-±1, ולכן `normScale × mesh.scale ≈ 1.000` בכל 15 הווריאנטים — יחידה מקומית אחת ≈ יחידת עולם אחת. כלומר **`anchorWorldScale` אמור לצאת קרוב ל-1**; חריגה משמעותית מסמנת שנלקח האובייקט הלא נכון (בפולו: 38.075).

לא לבלבל עם `unitsPerPx` עצמו — הוא יוצא בערך `0.006` (fov 30, מרחק ~5.5, קנבס ~400px).

### 5.4 ביצועים — הדרישה שמעצבת את המימוש

`DecalGeometry` עובר על **כל** משולש ברשת היעד וגוזר אותו מול 6 מישורים. drei בונה מחדש בכל שינוי של מספרי `position`/`scale`/`rotation` ([Decal.js:105](../../../node_modules/@react-three/drei/core/Decal.js#L105)).

**היעד הוא פרימיטיב אחד, לא המודל כולו.** `meshes` ממוין לפי מספר קודקודים ו-`bodyMesh = meshes[0]` ([Tshirt3DModel.tsx:752-762](../../../components/designer/three/Tshirt3DModel.tsx#L752-L762)); בפולו `targetFor` מנתב לפאנל הקדמי/אחורי. `DecalGeometry` לעולם לא רואה את כל המודל. הפער דרמטי — בפולו יש **40 פרימיטיבים**.

**החולצה היא החריגה היחידה:** 340k משולשים, פי 2.5 מהבא בתור, ו-**4fps** בבנייה מחדש לכל `pointermove`. כל השאר בין 24 ל-86ms. אבל החולצה היא `productId` ברירת המחדל והמוצר הנפוץ ביותר — ולכן זו דרישה חוסמת.

> **מסלול נסיגה** אם התצוגה האימפרטיבית מסתבכת: לא לוותר על הפיצ'ר, אלא לדלל (decimate) את פרימיטיב ה-Cloth של החולצה. הוא החריג היחיד.

**הפתרון: תצוגה מקדימה אימפרטיבית בזמן הגרירה, הטלה אמיתית אחת בשחרור.**

זה אפשרי כי ה-`<mesh>` ש-drei מרנדר **לא** מקבל את `position`/`rotation`/`scale` — הם מפורקים החוצה ([Decal.js:26-28](../../../node_modules/@react-three/drei/core/Decal.js#L26-L28)) ומשמשים רק לבניית הגיאומטריה. לרשת הדקאל טרנספורם זהותי, והגיאומטריה אפויה במרחב המקומי של הבגד. לכן אפשר להזיז ולשנות את קנה המידה שלה ישירות דרך ה-ref ש-drei מעביר (`useImperativeHandle`, שורה 32), בלי שה-effect יילחם — התלויות שלו לא כוללות את הטרנספורם של הרשת.

המטרה: לשחזר `v' = P + Δ + R·diag(sRel, sRel, 1)·Rᵀ·(v − P)`. לפי §4.1.1 ההצמדה מתאפסת, ולכן:

```ts
// bakedPlacement = ה-placement שהגיאומטריה הנוכחית נבנתה איתו (בסיס + ההסטה שכבר בוצע לה commit).
// committed      = הטרנספורם כפי שהיה ב-pointerdown / בתחילת גרירת הסרגל.
// live           = הערכים החיים, כבר חסומים (ראו למטה).
const P = bakedPlacement.position          // [x,y,z] — במרחב המקומי של רשת הבגד
const sRel = live.scale / committed.scale  // ← יחסי, לא מוחלט

const D = new THREE.Vector3(
  live.dx - committed.dx,                  // ← דלתא, לא סך הכול
  live.dy - committed.dy,
  0,
).applyEuler(new THREE.Euler(...bakedPlacement.rotation))   // ← חובה

decalMesh.scale.set(sRel, sRel, 1)         // ← לא setScalar
decalMesh.position.set(
  P[0] * (1 - sRel) + D.x,
  P[1] * (1 - sRel) + D.y,
  D.z,                                     // z לא מוקטן → אין איבר (1-sRel)
)
```

שלושה דברים שכל אחד מהם עובר בדיקה שטחית ואז נשבר:

1. **אסור `setScalar`.** הוא מפעיל `diag(s,s,s)` ומזיז כל קודקוד גם לאורך ציר z של המקרן. ב-`front_full` של החולצה (`P_z=0.3`, `depth=0.55`) הקודקודים ששרדו יושבים ב-`z ∈ [0.025, 0.575]`, ובפועל נחתכים ב-`z ≤ 0.416`. כבר ב-`s = 1.3` קודקוד אגף נכנס אל **תוך** הבד (`z = −0.058`), ועם `depthTest` דלוק ו-`polygonOffsetFactor={-6}` בלבד — הוא פשוט נעלם. המנהל רואה חתיכות מהעיצוב מתאדות תוך כדי הזזת הסרגל. הפתרון: `diag(s, s, 1)`.
2. **`sRel` ו-`D` חייבים להיות יחסיים למצב האפוי.** ה-`scale` שכבר בוצע לו commit אפוי בגיאומטריה דרך `artworkScale`, וההסטה שבוצע לה commit כבר נמצאת בתוך `P`. ערכים מוחלטים ⇒ `1.4 × 1.5 = 2.1` וקפיצה מיידית בכניסה לגרירה השנייה. **בלתי נראה באזור טרי, נשבר בכוונון השני.**
3. **`D` חייב לעבור את סיבוב המקרן.** בלעדיו, בגב `R_y(π)` לא מקוזז — גרירה ימינה מזיזה שמאלה. זה בדיוק הבאג ש-§4.1 קיים כדי למנוע, מוחזר דרך הדלת האחורית.

**איפוס בשחרור — שלב חובה.** ב-`pointerup` ה-props החדשים מגיעים ל-`<Decal>`, drei בונה גיאומטריה עם ההסטה כבר אפויה בפנים — ואם הטרנספורם של התצוגה המקדימה עדיין על הרשת, הדקאל **קופץ כפליים**. האיפוס (`position.set(0,0,0); scale.set(1,1,1)`) חייב לקרות באותו commit.

סדר הפעולות מובטח רק אם **`ShirtDecal` מחזיק את ה-ref** ומבצע את האיפוס ב-`useLayoutEffect` שתלוי במספרים שבוצע להם commit: `<Decal>` הוא **הילד** שלו, ו-React מריץ layout effects של ילדים לפני ההורה, כך שהבנייה של drei קודמת לאיפוס. מימוש שמניח את האיפוס ב-`DecalDragController` (אח, בתוך `Preview3DStage`) לא מקבל שום הבטחת סדר ומקבל הבהוב של פריים.

**החסימה מוחלת על הערכים החיים**, בזמן צבירתם ב-ref ולפני חישוב `D` — לא רק ב-commit. אחרת התצוגה עוקבת אחרי האצבע מעבר לגבול וקופצת אחורה בשחרור.

- **דיוק:** התצוגה החיה היא קירוב מסדר ראשון — הזזה שטוחה במקום הטלה מחדש על משטח מעוקל. בטווח ±0.35 על חזה/גב זה ויזואלית כמעט זהה, והתוצאה הסופית תמיד מדויקת.
- **הסינר** עובר במסלול `SheetShirtDecal` (mesh רגיל, לא `<Decal>`) ומקבל את אותו טיפול. זה עובד בזכות **צירוף מקרים שיש לתעד:** `useSheetDecalGeometry` בונה במרחב העולם של השיבוט, והתוצאה מרונדרת כילד של `<mesh>` שנושא `position/rotation/scale` — שני המרחבים מתלכדים **רק** מפני שלצומת ה-glTF של הסינר (`Apron_man`) אין TRS כלל. מודל `singleSheet` שני עם טרנספורם צומת לא-זהותי ישבור גם את ה-placements הקיימים וגם את התצוגה הזו.
- **4 חצי הכוונון** הם הקשות בדידות → בנייה אחת לכל הקשה. בחולצה ~248ms — מורגש אך נסבל; **בכל שאר המוצרים ≤86ms**, כלומר מיידי.
- **תוצר לוואי:** הערך החי נשמר ב-ref ולא ב-state, ולכן אין רנדר מחדש של העמוד וה-Canvas בכל `pointermove`.
- **הבחנה:** התיקון ב-§4.3 מונע בניות **מיותרות** ברנדרים לא-קשורים; התצוגה האימפרטיבית מונעת את הבנייה **לכל `pointermove`**. שני דברים שונים, שניהם נחוצים.

### 5.5 גבולות

`dx`, `dy` נחסמים ל-`±0.35`; `scale` ל-`0.3`–`2.0`.

**מה החסימה כן עושה:** מונעת מצב שבו העיצוב נגרר עד שאין מולו גיאומטריה, ה-`Decal` נעלם לגמרי, והמנהל נשאר עם תצוגה ריקה בלי להבין למה.

**מה היא לא עושה:** היא **לא** מבטיחה שהעיצוב נשאר על הבגד. לדוגמה, בווסט `back` יושב ב-y=0.42 עם מדריך בגובה 0.48 מול רשת שנפרשת ב-y ∈ [−1, 1] — `dy=+0.35` מוציא את ראש ההדפסה אל מעבר לכתפיים. כך גם בבאף ובכובע. זו רשת ביטחון, לא אילוץ שטח הדפסה; העין של המנהל היא הקובעת. גזירת גבולות מדויקים מ-`boundingBox` של כל רשת היא over-engineering לכלי אדמין.

## 6. ממשק המשתמש

הפאנל יושב **מתחת לתצוגה המקדימה**, באותו כרטיס — במובייל התצוגה נמצאת מתחת לטופס (`grid-cols-1 lg:grid-cols-2`), כך שהפקדים תמיד סמוכים למה שהם משפיעים עליו.

```
┌─ תצוגה מקדימה — מה שהלקוח יראה ─────────┐
│                                          │
│            [ מודל תלת-ממד ]              │
│                                          │
├──────────────────────────────────────────┤
│  סידור העיצוב:  (קדמי מלא) (סמל ימין)   │  ← רק אזורים שהועלה אליהם קובץ
│  ┌────────────────────────────────────┐  │
│  │  גררו את העיצוב על הבגד            │  │  ← מופיע רק כשאזור נבחר
│  │           ▲                        │  │
│  │        ◀  ●  ▶      גודל  ──○──   │  │
│  │           ▼            [אפס]       │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

| פקד | תפקיד |
|---|---|
| גרירה על הבגד | הזזה חופשית — `pointerdown/move/up` מטפל בעכבר ובאצבע זהה |
| 4 חצים | כוונון עדין, צעד `0.01` |
| סרגל גודל | `0.3`–`2.0`, צעד `0.05`; תצוגה חיה, commit בשחרור — ראו האזהרה מתחת לטבלה |
| אפס | מחזיר את האזור הנבחר ל-`{0, 0, 1}` |

> ⚠️ **`onChange` של React על `<input type="range">` אינו אירוע ה-`change` המקורי.** React ממפה `onChange` אל אירוע ה-**`input`**, כלומר הוא נורה בכל צעד של הגרירה — בנייה מחדש של 248ms לכל 0.05 בחולצה, בדיוק הסופה ש-§5.4 נכתב כדי למנוע, מוחזרת על ידי מימוש מילולי של "commit ב-change".
>
> **המפרט:** `onChange`/`onInput` → מעדכנים **רק** את ה-ref החי. ה-commit ב-`onPointerUp` **וגם** ב-`onKeyUp` — חצי מקלדת מזיזים סרגל ממוקד בלי שום אירוע מצביע.

בחירת אזור מסובבת אליו את המודל ונכנסת למצב עריכה. לחיצה חוזרת על אותו אזור יוצאת.

**החסימה תיתפס הרבה — וזה תקין.** `Bounds` מתאים את המודל (2 יחידות) לרוחב הקנבס, כלומר יחידה מקומית ≈ 200px, ו-`±0.35` ≈ **±70px** של תנועת אצבע בתצוגה של ~400px. העיצוב שנעצר תחת המצביע אחרי גרירה קצרה הוא רשת הביטחון עובדת, לא באג.

**מדריך האזור הנערך מוצג.** היום `GuideDecal` מסונן ב-`!uploaded.has(a)` ([Tshirt3DModel.tsx:861](../../../components/designer/three/Tshirt3DModel.tsx#L861)), כלומר דווקא באזור שנערך אין מסגרת. במצב עריכה המדריך של `editArea` יוצג — **ללא** הטרנספורם, כדי לשמש ייחוס לשטח ההדפסה החוקי.

**חצים ב-RTL:** העמוד `dir="rtl"`. החצים ממופים לכיוון **על המסך** (חץ ימין = +dx), לא לכיוון לוגי, כדי שלא יתהפכו.

**ניקוי state.** הטרנספורם של אזור נמחק בכל מקום שבו הקובץ שלו נמחק:

| פעולה | טיפול |
|---|---|
| `selectProduct` — החלפת מוצר | ניקוי מלא |
| `selectType` — החלפת סוג בד | ניקוי אזורים שנפלו מ-`areaFilter` |
| כפתור X — הסרת קובץ | מחיקת הטרנספורם של אותו אזור |
| `resetAll` — "סקיצה חדשה" | **ניקוי מלא** — בלי זה טרנספורם דולף לסקיצה הבאה על אותו `areaId` |
| העלאת קובץ חדש לאזור שכבר יש לו טרנספורם | **הטרנספורם נשמר** — בדרך כלל מדובר בהחלפת אותה אומנות בגרסה מתוקנת, ואיפוס היה מוחק עבודה. "אפס" זמין תמיד |
| הסרת רקע / ביטול הסרת רקע | הטרנספורם נשמר — אותה אומנות |

## 8. מקרי קצה

| מקרה | התנהגות |
|---|---|
| סקיצה ישנה בלי `transform` | נרנדרת כמו היום — `withTransform` מחזיר את ה-placement המקורי (כולל זהות אובייקט) |
| אזור בלי `GuideBox` (`center`, `center_wide`, `CAP.front_full`) | מסלול ה-fallback ב-`artworkScale`, שגם עליו מוחל המכפיל (§4.2) |

| העיצוב נגרר לקצה | חסום ב-`±0.35` (§5.5) |
| יציאה מהעמוד באמצע גרירה | מאזיני `pointermove/up` על `window`, מנוקים ב-cleanup — כמו ב-`Turntable` היום |
| **WebGL נכשל אצל הלקוח** | `ThreeErrorBoundary` בעמוד השיתוף מרנדר `MockupView` דו-ממדי לפי `DESIGN_AREA_OVERLAYS`, שלא יודע על `transform`. **מקובל במודע:** זו כבר תצוגה מנוונת שלא תואמת את התלת-ממד גם היום. אין שינוי התנהגות, רק תיעוד המגבלה |
| `ThreeErrorBoundary` באדמין | אותו דבר — `<img>` גולמי, בלי טרנספורם. תצוגת חירום בלבד |
| שני אזורים חופפים בכובע (`center` + `center_wide`) | קיים מראש; בורר האזורים החדש יחשוף את זה אך לא יחמיר. מחוץ להיקף |
| יציאה ממצב עריכה | `focusArea={editArea ?? activeArea}` הופך ל-`undefined`, ה-effect נורה, והמודל מסתובב חזרה לחזית. **שינוי התנהגות גלוי ומכוון** — מסיים את העריכה בתצוגה הקדמית |

## 9. אימות

הבדיקות מורצות על ידי Claude, לא על ידי המשתמש.

1. `npx tsc --noEmit` — נקי (שימו לב להצרת `PerspectiveCamera`, §5.3).
2. `npm run build` — עובר.
3. **ביצועים — חוסם:** מדידת קצב פריימים בגרירה על `/admin/sketches` עם **חולצה** (יעד דקאל 340k משולשים — המקרה הגרוע ביותר). גרירה חלקה, ובנייה מחדש אחת בלבד בשחרור. בלי המדידה הזו §5.4 לא נחשב עבר.
3א. **גודל:** הזזת הסרגל עד `2.0` בחולצה — אף חלק מהעיצוב לא נעלם אל תוך הבד (הבאג של `setScalar`, §5.4).
3ב. **כוונון שני:** לכוונן אזור, לשחרר, ואז לכוונן שוב — אין קפיצה ואין הכפלת גודל (הבאג של ערכים מוחלטים, §5.4).
3ג. **גב:** בעריכת אזור `back` — גרירה ימינה מזיזה ימינה על המסך, גם בתצוגה החיה וגם אחרי השחרור.
4. דסקטופ: העלאה → בחירת אזור → גרירה מזיזה → חצים בצעדים → סרגל משנה גודל בלי מתיחה → אפס מחזיר.
5. יציאה ממצב עריכה → גרירה אופקית שוב מסובבת.
6. כניסה חוזרת לאותו אזור אחרי סיבוב ידני → הכיוונים עדיין נכונים (§5.2, מלכודת שנייה).
7. מובייל (אמולציית מגע): גרירה אנכית במצב עריכה מזיזה ולא גוללת; אחרי יציאה — גוללת שוב.
8. יצירת סקיצה → פתיחת קישור השיתוף → מיקום וגודל זהים לאדמין.
9. רגרסיה: סקיצה **בלי** כוונון נראית זהה למצב שלפני השינוי; `/designer/tshirt` לא הושפע; מדריכי הכובע לא השתנו (§4.4).
10. רגרסיה ממוקדת: **סינר** (`singleSheet`) ו**פולו** (`panels`) — מסלולי רינדור נפרדים.
11. **גרירה בסינר במפורש** — זה מסלול ה-ref היחיד שאינו של drei אלא `<mesh geometry={geo}>` ידני, הרוכב על צירוף המקרים של `Apron_man` (§5.4). ובנוסף: אין דליפת גיאומטריה בגרירה ממושכת (§4.3).
12. **עמידות ל-null:** `ShirtDecal` מחזיר `null` עד שהטקסטורה נטענת, ו-`SheetShirtDecal` מחזיר `null` אם אין גיאומטריה. גם ה-`useLayoutEffect` של האיפוס וגם בקר הגרירה חייבים לסבול `ref.current == null`.
